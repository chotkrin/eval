# MDX LiveCodeBench scoring and evaluation summaries

The GPU evaluation scripts generate model outputs but **do not execute generated
programs**. Both model families are supported:

- LLM-jp: `EVAL_OUTPUTS/<experiment>_16/livecodebench_v6/lcb_custom.json`
- Phi/DSDT: `EVAL_OUTPUTS/<experiment>_16/livecodebench_v6/*_lcb_custom.json`

Two new shell scripts each own an editable `EXP_NAMES=(...)` list; those lists
are independent. The defaults match `sh/mdx/eval_llmjp.sh` (exp004 and SFT).

## Step 1: score Code with official LiveCodeBench

Run on an **isolated CPU container/VM with no network or secrets**, not on a
shared login node or an unisolated Slurm worker. Official LiveCodeBench executes
**untrusted model-generated code**. Slurm resource allocation alone is not a
security boundary. Install the official LiveCodeBench checkout at `LCB_ROOT`
(from `.env`) and make its `lcb_runner` importable using the **same uv Python**
used by the evaluation project. Ensure necessary runner dependencies are
available in the shared uv environment before scoring. A separate LCB venv is
not used. Cache the official benchmark dataset ahead of network isolation.

```bash
cd /home/zelin/code/eval_math_lcb_direct
# Inside an isolated environment only, explicitly acknowledge the risk:
LCB_ACK_UNTRUSTED_CODE=1 bash sh/mdx/score_livecodebench.sh
```

Settings: `LCB_N=16`, `LCB_RELEASE_VERSION=v6`, `LCB_NUM_PROCESSES=4`,
`LCB_TIMEOUT=6`, `LCB_TEMPERATURE=0.6`. Use `LCB_FORCE_RESCORE=1` to rerun
existing scores. The `v6` tag means only new v6 questions, **not** cumulative
`release_v6`. The script rejects release-version mismatches.

For each experiment, the script ensures there is **exactly one** custom JSON in
its LiveCodeBench v6 directory. If the expected official score files are
missing/invalid/stale, it invokes `lcb_runner.runner.custom_evaluator` and
writes a `*_codegeneration_evaluation.log` next to the input. It verifies the
result after completion. Existing valid scores are skipped. Scores are not
considered complete just because a file exists: question IDs, candidate counts
and associated output JSON must also match. For older results with multiple hashed directories, run `bash analysis_results/migrate.sh --apply`
first; only the chosen winner is kept under the live dataset directory, while other
runs are archived outside it.

If the upstream LiveCodeBench checkout cannot load incremental v6 data (some
versions still call a legacy Hugging Face dataset script), scoring **fails
visibly** with the error in its log. Do not switch to `release_v6` to bypass
a length mismatch; fix or pin that upstream loader for the same v6 questions.

## Step 2: make the three-level summary

```bash
bash sh/mdx/summary_eval.sh
```

Output is printed to the console and saved to
`$EVAL_OUTPUTS/eval_summary_n16.csv`, unless `SUMMARY_CSV` is set. One record
per dataset, one per category (`Math`, `Code`, `MC`), and one total record per
experiment.

- **Dataset:** `acc` (first sampled answer accuracy for math/MC), `pass@1`,
  `pass@5`, `pass@10` where reported, and the number of questions. Official LCB
  scores use a 0–1 scale and are converted to 0–100 percentages.
- **Category:** unweighted macro-average of the datasets in that category;
  category averages are *not* weighted by dataset sizes.
- **Overall:** mean of the three category averages with **equal weights**
  (Math / Code / MC). This is category-balanced, not a question-weighted rate.
- **Missing/ambiguous/unfinished:** `PARTIAL` status and `NA` aggregate,
  never silently treated as zero or averaged from a subset of datasets.
- **`acc` overall:** `NA`, because LCB supplies `pass@1`, not the legacy
  first-sample `acc` field. `pass@1` is the comparable cross-category metric.

Data sets: Math = math500, aime24, minerva_math, olympiadbench, amc23, aime26;
Code = livecodebench_v6; MC = gpqa_diamond and mmlu_stem. Changing the data
suite requires changing `DATASETS` in `sh/mdx/lcb_results.py` as well.

If any dataset is missing, the summary command exits nonzero after writing its
partial CSV, suitable for CI/checks. Both scripts look for
`EVAL_OUTPUTS/<experiment>_<LCB_N>`, as generated by MDX submission scripts.
